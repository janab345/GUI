## 0. The honest starting point

You are being asked to absorb three new things at once: a domain (space), a
rendering stack (Three.js / R3F), and an AI-written codebase. A senior would cut
that to **one new thing at a time**.

Good news: roughly 80% of this project is web development. React, state, props,
keyboard events, CSS, build tooling, debugging — you already have those. The new
20% is:

1. **Frames and units** (where is "up", what is "altitude")
2. **Attitude** (how the ship is rotated, stored as a quaternion)
3. **A small amount of landing vocabulary** (PDI, thrust, TWR, Δv)

Python, orbital mechanics, MATLAB, and reinforcement learning are **not** on the
critical path for this sprint.

---

## 1. The whole app in one paragraph

> You press arrow keys. Those keys become two commands: `throttle` and `rcs`
> (tilt left / right). A pure function `stepState()` takes the current vehicle
> state plus those commands, advances time by one small step, applies the
> current physics rules (today: throttle, tilt, fuel; next: gravity and thrust),
> and returns a new state. The 3D scene and the HUD both simply **draw** that
> state. Nothing else simulates.

Every file in the repo is one of four things: **input**, **math**, **state**, or
**drawing**. If you can point at which file does which, you understand the
architecture.

## 2. Vocabulary you actually need (nothing more)

| Term | Plain meaning | Where it appears |
|---|---|---|
| **PDI** | Powered Descent Initiation — the moment the landing burn starts, ~15 km up | Mission profile starts at "Braking" |
| **Attitude** | Which way the ship is *pointing* (not where it is) | The 3D model rotating |
| **Thrust** | Force from the engine, in newtons (currently normalized 0–1) | Flame size, `thrustOf()` |
| **Throttle** | How much of max thrust the operator commands, 0–100% | Up/Down keys, throttle bar |
| **RCS** | Reaction Control System — small jets that rotate the ship | Left/Right keys, blue jets |
| **Gimbal** | Engine tilts slightly to steer without turning the whole ship | Not implemented; out of scope |
| **TWR** | Thrust-to-Weight Ratio. ≤ 1 means you cannot stop falling | Not displayed yet; worth adding |
| **Δv (delta-v)** | Total speed-change budget available in the tanks | Later; explains why fuel matters |
| **HUD** | Head-Up Display. An overlay of numbers on top of the 3D view — plain React DOM, not 3D | `Hud.tsx` |
| **Phase** | A stage of descent with its own rules (Braking → Terminal) | `MissionProfile.tsx` |
| **Telemetry** | The numbers the vehicle reports: altitude, speed, fuel | `HealthStatus.tsx` |
| **Target** | The landing pad coordinates being aimed at | `state.target` |
| **Miss distance** | Distance from touchdown point to target | Not implemented yet |
| **Slerp** | Spherical linear interpolation — smooth blend between two rotations | `Scene3D.tsx` |

That is the full MVP vocabulary. Orbital mechanics, perturbations, guidance
laws, and atmospheric entry come later and are not needed to ship the demo.

## 3. The physics — five equations

The Moon is simpler than Earth for a lander: **no air, no drag, no parachutes,
constant gravity near the surface.** All braking is propulsive.

1. **Gravity.** `a_g = 1.62 m/s²` downward, everywhere near the surface.
   In a Y-up frame: `[0, -1.62, 0]`. In ENU: `[0, 0, -1.62]`.
2. **Thrust acceleration.** `a_t = F / m`, along the ship's thrust axis.
3. **Integration.**
   `a = a_t + a_g` → `v += a * dt` → `p += v * dt`.
   That is the entire simulation. Everything else is bookkeeping.
4. **Mass flow.** `dm/dt = -F / (Isp * g0)`, with `g0 = 9.81 m/s²` and `Isp`
   around 300 s for a lunar descent engine. Burning fuel makes the ship lighter,
   so the same throttle later produces more acceleration.
5. **TWR.** `TWR = F / (m * 1.62)`. Below 1, gravity wins and the ship
   accelerates downward. At 1, it can hover. Only above 1 can it arrest a
   descent.

**Why attitude is the steering.** With no atmosphere and a fixed engine, thrust
points where the nose points. Rotating the ship redirects thrust. Killing
horizontal velocity is an attitude problem, not a throttle problem. That is the
actual skill this trainer teaches.

**Current code status:** there is no gravity and no translation. Velocity is a
constant `[0, 0, 200]` and position never changes. The ship rotates, the flame
changes, and fuel drains. This is "visualization mode" and is intentional for
Day 1, but it means altitude and speed never change. Adding equations 1–3 is the
single biggest step forward and is roughly 30 lines.

## 4. Quaternions without the math

First, terminology: **Euler angles** are roll / pitch / yaw. **Euler's formula**
(`e^{iθ}`) is complex analysis and irrelevant here.

**Problem with Euler angles:** at pitch ±90° the axes collapse (gimbal lock), and
interpolating between two angle triples takes unintuitive paths.

**Fix:** store rotation as **four numbers whose length is 1** — a quaternion.
No gimbal lock, smooth interpolation.

What you need to *use* a quaternion — not derive it:

| Operation | Meaning | Code |
|---|---|---|
| Store | four numbers | `state.quaternion` |
| Compose | "rotate by A, then B" | `qA.multiply(qB)` |
| Invert | undo a rotation | `q.conjugate()` (unit q only) |
| Normalize | keep it valid after integration | `q.normalize()` |
| Blend | smooth transition between rotations | `slerp` in `Scene3D.tsx` |
| Apply | rotate a direction vector | `v.applyQuaternion(q)` |
| Tilt | how far the body leans left/right | `tiltDeg()` in `vehicle.ts` |

**The order trap.** Three.js stores quaternions as `(x, y, z, w)`. Most GNC,
Python, and MATLAB code uses `(w, x, y, z)`. Same numbers, different order.
This repo uses Three's order. Write it down once; it is the most common silent
bug when a Python plant is connected later.

You do **not** need to derive quaternions for this job. You need to recognize
them and know which library expects which order.

**Current control axis.** The only attitude command today rotates about **+Z**
(the axis pointing out of the screen in the default camera view). Visually the
rocket leans left/right. With the model's long axis on `+Y`, a purist would call
this *roll*, not pitch; in the current 2D-style view it behaves as the lateral
tilt that steers thrust. The terminology is flagged in
[DECISIONS.md](./DECISIONS.md) (D-004) and must be settled before the real 3D
attitude work starts.

## 5. Frames and units

A **frame** is an origin + three axis directions + units. "Altitude = 15000" is
meaningless without saying *from where, along which axis, in what units*.

Pick exactly two frames and write them on a sticky note:

- **World frame** — recommended: local **ENU** at the landing pad.
  `x = East`, `y = North`, `z = Up`, origin at the pad, meters.
- **Body frame** — fixed to the ship. In the current model: `+Y` is the long
  axis (up), thrust is `-Y`, the green nose boom points `+Z`, and legs hang
  below. Attitude commands currently rotate about `+Z`, which leans the body in
  the screen plane.

Rules:

- Gravity in ENU is `[0, 0, -1.62]`. If altitude is on `y` (Three.js), gravity is
  `[0, -1.62, 0]`. Mixing these up produces "the ship falls sideways".
- Three.js is **Y-up**; ENU is **Z-up**. The conversion must live in exactly one
  function, not scattered across components.
- Put units in variable names: `altitude_m`, `vel_mps`, `thrust_n`. A plain
  `position` hides the bug.
- Degrees only at the display boundary; radians inside.

**Current code status:** no explicit frame. It is de facto Three.js Y-up:
altitude = `position[1]`, horizontal plane = `(x, z)`; the only attitude axis is
`+Z`, reported as a signed left/right tilt.
This is documented in [DECISIONS.md](./DECISIONS.md) so it is no longer implicit.

## 6. System design in five boxes

Draw this by hand once:

```
[1 INPUT]         [2 PLANT]           [3 STATE]          [4 VIEWS]
 keyboard   ──►   step(state, dt,  ──► one message   ──►  3D scene
 buttons          command)             (the contract)     HUD
 gamepad              │                                    trajectory plot
                      │                                    mission timeline
                      ▼
                [5 TIME / TRANSPORT]
                fixed dt · sim clock · later WebSocket
```

Five rules that answer most "where does this code go?" questions:

1. **One owner of state.** Currently `useVehicle.ts`. Views never keep copies.
2. **Views never simulate.** Physics inside `Scene3D.tsx` is a bug.
3. **Inputs are commands, not mutations.** A keypress becomes
   `{ throttle: 1, rcs: 0 }`; the plant decides what it means.
4. **Fixed timestep.** Advance physics in fixed 10 ms chunks, not monitor
   refresh intervals. Store `t_s` in state. This enables replay and tests.
5. **One seam.** `SimAdapter` with `reset()` / `step()`. Today TypeScript; later
   a WebSocket client to Python. The UI must not care which.

That is "system design before programming": boxes, arrows, ownership, one
interface. No UML or database diagram required.

## 10. Working with AI so you actually own the code

1. **Never merge a line you cannot explain in one sentence.** Ask:
   *"Explain this file as if I am reviewing it. What did you assume about frames,
   units, and quaternion order?"*
2. **Ask for diffs, not whole files.** One concept per commit.
3. **Force proof.** *"Write a test that proves gravity works. Show expected
   numbers and the hand calculation."* If it cannot produce verifiable numbers,
   it is guessing.
4. **Reject `as any` and `@ts-ignore`.** They hide a misunderstanding.
5. **Keep `nt/DECISIONS.md` current.** One line per decision plus reason. It is
   both your handover doc and your interview defense.
6. **Have the AI quiz you.** *"Ask me five questions about how this repo works
   and grade my answers."* Painful, effective.

## 13. Trainee trap to avoid

The failure mode here is not lack of knowledge. It is trying to learn the whole
domain before touching the code. You do not need to. You need **one frame, one
quaternion order, five equations, and the five-box diagram**. Everything else is
look-up-able, and your team expects you to look it up.
